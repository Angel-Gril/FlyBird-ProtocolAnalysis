# 部署验收清单（首个真实 HTTP 200 之后执行）

> 目的：把"能不能推 GitHub / 能不能说部署成功"变成可复核的门禁，而不是凭感觉。
> 每条都给出命令、通过标准和证据产物。

---

## Gate 0 · 合规与范围（每次跑之前）

- [ ] 目标面板已获书面授权（G-Auth），测试账号可用
- [ ] 不在生产环境做写操作（不改密码、不改套餐、不触发支付）
- [ ] 抓到的任何 token/key **不进仓库**，只进本地 `out/`（.gitignore）

## Gate 1 · 上游可达

```bash
python poc/probe_v2.py --hosts fbaxapi.web.ak005.com,fbaxapi.apiv2.a047.com
# 或持续盯：
python poc/watch_v2.py --hosts fbaxapi.web.ak005.com,fbaxapi.apiv2.a047.com \
  --paths /v2/site/settings,/v2/announcements/list --interval 30 --max 120 --out watch_out
```

- **通过**：任一端点返回 `200/401/403/405/422`（路由存在）
- **证据**：`watch_out/hits.jsonl` + `<ts>_<host>_<path>.body/.headers.json`

## Gate 2 · 响应保真

- [ ] `raw_body.bin` 与 HTTP body **字节一致**（未被 `res.text()` 破坏）
- [ ] 记录了 `content-encoding`（gzip 需在解密前处理）
- [ ] 记录了 `apex-sub-v2` / `apex-sub-sign-v2` 等响应头

- **通过**：`sha256sum raw_body.bin` 与抓包工具（或 `watch_v2` 保存的 `.body`）一致

## Gate 3 · 信封对齐

```bash
python poc/apxs_try.py --body out/raw_body.bin --credential out/credential.json \
                       --headers out/response_headers.json --out out/apxs
```

- **通过**：输出命中组合（`layout` + `key_candidates` + `aes-gcm[...]`），并落出 `yaml_*.yaml`
- **证据**：把命中的「布局 / 密钥派生 / 签名作用域」写进 `apxs_meta.json`

**已知三种布局**：`nonce12+ct+tag16`、`tag16+nonce12+ct`、`nonce12+tag16+ct`；
密钥派生：`raw / base64decode / hexdecode / SHA256(utf8) / SHA256(decoded)`；
签名作用域：`ciphertext` 或 `plaintext`，编码 `hex` 或 `base64`。

## Gate 4 · 双实现一致

- [ ] 你的 `src/apxs-v2.js` 解同一份 `raw_body.bin` 得到**逐字节相同**的 YAML
- [ ] Python `apex_crypto.decrypt_subscription()` 结果一致
- [ ] `verifyApxsV2Signature` 对真实签名返回 true；篡改 1 字节后返回 false

- **通过**：两者 `sha256(plaintext)` 相同；负例失败

## Gate 5 · 凭据生命周期

- [ ] 记录 `access_key` 的 `expires_at`（如果返回）
- [ ] 连续两次 `access-token → download` 均成功（确认非一次性）
- [ ] 只用 `access_key`（不带 Bearer token）也能下载（确认凭据可独立复用）
- [ ] `access_key` 失效时的错误码已记录（401/403/404？），并实现了重新换 key 的分支

- **证据**：`apxs_meta.json` 增加 `credential_expires_at`、`download_attempts`、`reused_without_session`

## Gate 6 · 节点可用性

- [ ] YAML 可被 mihomo 解析（`ApexCore -t -f fb_clash.yaml` 或等价校验）
- [ ] 节点数 ≥ 期望值（例如 74），且 `type` 分布符合预期
- [ ] 随机抽 2 个节点做 TCP 443 连通性测试（不建连、不做业务）

- **证据**：`nodes.json`（节点名/类型/端口，脱敏 server 域名）

## Gate 7 · 分发与降级

- [ ] `last-good` 缓存生效：上游 404 时仍能分发上一版
- [ ] 解密/验签失败时**不覆盖** last-good（fail-closed）
- [ ] 错误可观测：日志里有状态码、body 长度、命中的 layout

## Gate 8 · 仓库卫生

- [ ] `git grep -nE '(access_key|encrypt_key|sign_key|token)\s*[:=]\s*["'\'']?[A-Za-z0-9+/=_-]{16,}'` 无命中
- [ ] fixtures 里的 key 全是合成值；节点域名改成 `*.invalid`
- [ ] 二进制白名单 = `tests/fixtures/apxs/**/*.bin` + ≤1 MiB + 仅该目录
- [ ] `live_verified` 字段：拿到 200 才置 `true`，并记录 `captured_at`

## Gate 9 · 推送与声明

- [ ] Gate 1–8 全绿
- [ ] PR 描述里附：上游证据（状态码+时间）、`apxs_meta.json`、节点数、失败时行为
- [ ] 两个仓库分别确认状态（Network-About-Third-party-Proxy-Software / FlyBird-Link）
- [ ] 未通过任何一条 → 不推、不写"已部署"
