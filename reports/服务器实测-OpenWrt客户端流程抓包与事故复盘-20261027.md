## 一、抓到的真实请求链（TLS 终止观察，实证）

客户端 `/start` 时会按序发出：

| # | 方法 | URL | 关键头 | 实测响应 |
|---|---|---|---|---|
| 1 | GET | `https://tcdn-ax.getxlx.com/saos/apos/fb_apexv2.json?t=<毫秒时间戳>` | `User-Agent: ua.net.fbclient.app.apex/v7.2.4`、`Cache-Control: no-cache, no-store`、`Pragma: no-cache` | **500**（该主机当前全部路径 500） |
| 2 | GET | `https://fbaxapi.apiv2.a047.com/v2/feed/access-token` | 同上 + **`Authorization: <JWT 原文>`（不带 `Bearer ` 前缀）** | 正常 200（需按序） |
| 3 | GET | `/v2/feed/download?access_key=<access_key>`（subscription 主机） | UA + mTLS 客户端证书 | 200 APXS |

要点：**`/v2/feed/access-token` 用的是裸 JWT，不是 `Bearer <jwt>`**。这一点与之前所有手写脚本都不同。

## 二、可用的备用配置端点

```
https://oss-aws01.llguangli25n.com/apos/fb_apexv2.json        → 200，6692 B
```

解码链：
```
响应体(ASCII) --base64--> 5019 B（仅 128 种字节值，7bit）
             --base64--> 1451 B 二进制（246 种字节值，熵 6.65）
```
即 **base64(base64(密文))**，密文层用包内 137 个 base64 常量做 AES-GCM / XOR 均未命中
→ 与 APXS 同结论：**密钥由服务端按部署下发，不在二进制内**。

同主机 `/saos/apos/fb_apexv2.json` 返回 404（只有 `/apos/` 路径有效）。

## 三、订阅接口的真实放行条件（重要纠正）

之前"美国出口被 404"的判断**错误**。实测在硅谷服务器上：

```bash
# 三要素缺一不可
curl --cert 订阅证书 --key 私钥 \
     -A "ua.net.fbclient.app.apex/v7.2.4" \
     "https://fbaxsub.apiv2.a047.com/v2/feed/download?access_key=<key>"
# → 200 APXS

# 只少 UA   → 404（nginx 伪装页）
# 只少证书   → 404
```

`fbaxsub.apiv2.a047.com` 与 `fbaxsub.web.ak005.com` 均解析到 `<overseas-edge-ip>`
（`axapi-overseas.*`），两者行为一致。

## 五、事故复盘（必须记住）

**触发条件**：客户端 `transparent` 默认 `true`。在**非 OpenWrt 宿主**上 `/start` 会：

```
nft table inet apex_mihomo   +   ip rule pref 10999   +   ip route table 2026
```

本机还叠加了 `GOGC=off`（1.6G 内存）。

**后果**：宿主机出站流量被 tproxy 劫持，sshd / nginx 响应发不出；
外网表现为「TCP 三次握手成功，应用层零数据」。控制台显示实例"运行中"，但业务不可用。

**恢复**：控制台强制重启 → 补清理（hosts / CA / 目录 / swap）。

**最终校验（已全部通过）**：

| 项 | 结果 |
|---|---|
| `/etc/hosts` | 恢复为 9 行标准内容，无测试条目 |
| 测试 CA | 已删除，CA 库 120 条，无 probe 软链 |
| nft / iptables / ip rule | 无 `apex_mihomo`、无 `<ip>`、无 `pref 10999` |
| 测试目录 | `/root/apextest`、`/tmp/probe`、`/usr/share/apex-mihomo`、`/tmp/apex-mihomo` 全部删除 |
| 进程 | 无 `mihomo` / `mitm_*` 残留 |
| swap | `/swapfile 2G` 已重新启用 |
| 服务 | ssh、nginx 均 active |
| 出网 | baidu 200 / google 200 / aliyun 302 |
| 站点 | `sub.20260610.xyz` 404、`proxies.20260610.xyz` 302（TLS 正常） |

## 六、下次重跑的硬性约束

1. **必须 `transparent=false`** 再 `/start`；
2. **不要 `GOGC=off`**（1.6G 内存撑不住）；
3. **必须在独立 network namespace 里跑**（`unshare -n` + `slirp4netns`/`veth`），
   让它的 nft/ip rule 只作用于 netns 内部；
4. 先用 `iptables -t nat -S | grep apex`、`nft list tables` 做跑前跑后对照；
5. 任何 hosts / CA 改动都要有 `trap restore EXIT` 兜底。

## 七、结论

- 官方 OpenWrt 客户端**确实存在、可启动、可登录、具备 APXS 解密能力**；
- 当前阻塞**不是**地域封锁，而是**配置端点 `tcdn-ax.getxlx.com` 全线 500**，
  备用 OSS 端点返回的加密配置需要服务端下发的密钥；
- 因此「靠客户端自身跑通全链路」在本机尚未成功，仍需：
  (a) 等 `tcdn-ax` 恢复，或 (b) 拿到 `identities` 密钥自行解密 OSS/APXS。
