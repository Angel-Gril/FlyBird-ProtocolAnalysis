# 11 · 7.3.1 更新差异与协议回归（`fbapp-speed.exe` 2026-11-23 构建）

> **脱敏说明**：本报告为可公开版本。节点主机名、随机 SNI、节点口令、账号邮箱、access_key/JWT 与精确流量数字均已移除或占位化；样本与中间产物不入库（见 `docs/10-family-roadmap.md` §10.4）。所有结论均可由 `tools/windows/` 下的脚本重跑。

> 样本：`fbapp-speed.exe`（Windows 安装包）
> 上一轮基线：`reports/fbapp-speed-逆向分析报告.md`（7.2.3）+ CHANGELOG `[1.1.0]` 的 7.2.5 结论

### 3.2 APXS v2 信封（未变）

```
[0:4]  "APXS"        [4] 0x02      [5:9] BE u32 aesKeyID=1
[9:13] BE u32 signKeyID=1          [13:25] nonce(12)
[25:L-80] AES-256-CTR( k1, nonce‖0x00000002 ) 密文
[L-80:L-64] 16 B（非 GCM tag）      [L-64:L] 64 B Ed25519 签名
```

本轮用 `k1` 走了一遍**构造→解密**闭环（170 B 信封 → 65 B 明文），`aesID/signID` 均为 1，往返逐字节一致。verifier 见 `tools/windows/verify_build.py`。

> 仍然不是 GCM AEAD：把尾部 16 B 当 tag 验、把 AAD 拼头部，全部必然失败（`docs/04 §4.8` 已定性）。

### 3.3 mTLS 客户端身份（未轮换）

### 3.4 证书基线：从"有码无数据"到"有码有数据"

`app.so` 内新增 3 张公共根 CA（base64 DER，非 PEM 块）：

| 根 CA | 偏移 | 有效期 | SHA-256 |
|---|---|---|---|
| SSL.com TLS RSA Root CA 2022 | `0x00409840` | 2022-08-25 → 2046-08-19 | `8faf7d2e…c17f2ed` |
| ISRG Root X1 | `0x0042FEF0` | 2015-06-04 → 2035-06-04 | `96bcec06…ddf08c6` |
| ISRG Root X2 | `0x0045F760` | 2020-09-04 → 2040-09-17 | `69729b8e…cb1470` |

配套字符串（均在 `app.so`）：

```
0x003DAA20  Certificate pinning is enabled but certificate failed to load. Refusing connection for security reasons.
0x005E6F10  Certificate pinning is enabled but no expected certificate is available. Refusing connection for security reasons.
0x0050F150  Bundled public CA fingerprint mismatch
0x004B5020  Bundled public CA requires a trust-program review
0x006889A0  Bundled public CA is explicitly distrusted by Windows
0x00562A30  ssl_com_tls_rsa_root_ca_2022
0x0061AA60  assets/cer/client-cert.crt
```

判读：

- 7.2.3 的结论是"pinning 有代码、无数据（`assets/cer/` 空）"，**该结论在 7.3.1 需要修订**：数据已随包内置，检查对象从"预期站点证书"扩展为"内置公共根 CA 基线"。
- 是否**生效**仍由远程配置里的证书配置项驱动（`getCertificateConfig` / `configFingerprint`），本轮未能取到 `fb_apexv2.json`，故不下"已强制 pin"的结论。
- 对旁路提取的影响：**本地解密链路完全不受影响**（`k1` 是纯离线运算），受影响的是"用自签 CA 做 TLS 终止观察"这条取证路线——若 pinning 被配置打开，`tools/mitm_observe.py` 需要把自签 CA 同时挂进客户端的信任基线，否则握手会被主动拒绝并记录 `certificate_untrusted`。

#### 3.5.1 门禁实测：配置 CDN 要的是 **oss** 证书

镜像的 TLS 层是通的，但 `api` / `subscription` 证书一律拿 `nginx 404`（153 B 伪装页）——**换成 `oss` 证书立刻 200**：

| 证书 \ 目标 | `apisa-ax.cnossfile.com/apos/fb_apexv2.json` |
|---|---|
| 无 | 404（153 B） |
| api | 404 |
| subscription | 404 |
| **oss** | **200 / 7244 B / application/json** |

> 这条修正了 7.2.3 阶段"oss 主机 500，配置拿不到"的记录：不是主机坏，是**当时没带 oss 证书**。

**TLS 层的真实情况（2026-11-23 复核，`--allow-expired` 之外一律严格校验）**：

| 镜像 | 叶子证书 | 有效期 | 严格校验 | 结果 |
|---|---|---|---|---|
| `apisa-ax.cnossfile.com` | `*.cnossfile.com`（Let's Encrypt, CN=E7） | 2026-03-31 → **2026-06-29（已过期）** | ✗ code=10 | 跳过 |
| `cdno01-ax.llguanglisf.com` | — | — | 连接被 RST | 跳过 |
| `tcdn-ax.getxlx.com` | `*.getxlx.com`（Let's Encrypt, CN=YR2） | 2026-10-27 → 2027-01-25 | ✓ | **200 / 7244 B** |
| `ocdn01-ax.llguangli25o.com` | — | — | 连接被 RST | 跳过 |

> **对上一版的更正**：上一版写"系统 DNS 给的是被污染地址、要用 DoH 换 IP"——**这条不成立**。
> 实测 `tcdn-ax.getxlx.com` 走**系统 DNS**（`103.236.73.19`）直接 200；而用 DoH 换到
> `222.186.134.196` 反而 404。也就是说"换 IP"是把可用路径换坏了，`fetch_config.py`
> 已改为**只按主机名解析**，IP 只允许 `--resolve HOST:IP` 显式覆盖，代码里不写死任何地址。
> 完整实现与策略见 `tools/windows/fetch_config.py`（严格 TLS / 签名策略 / DNS+DoH 兜底）。

#### 3.5.4 信封新增 `signature`

`signature` 为 **64 B** 的 base64（88 字符），形态与 Ed25519 签名一致（`apex-sub-sign-v2` 用的是同一族算法）。

本轮验证矩阵：3 把内置常量（k1/k2/k3）× 13 种消息构造（`payload` 原串 / `payload` 解码后 / `format+payload` / `format|payload` / 去签名字段重序列化 / `sha256(payload)` / 原始体 / XOR 前体 …）**全部不匹配**；
再把 `app.so` 里能扫到的 29 个 32 字节候选（44 字符 base64 + 64 字符 hex）逐个当公钥试，**0 命中**。

结论：**配置签名用的是独立的一把验签公钥**（很可能与 XOR_KEY 一样按构建注入，未被 7.3.1 的明文常量暴露）。
影响：F3「远程配置零签名」这一条在 7.3.1 已被厂商修掉一半——现在有签名，只差"是否强制验签"的运行时确认（静态看不到校验分支的失败处理，需要断点或改包试验）。

### 8.4 节点面的 DNS 与可达性（值得单独记一笔）

| 查询 | 结果 |
|---|---|
| `axbtapp-…llguanglisf.com` A/AAAA（alidns DoH） | 仅 CNAME → `abappls-<edge>.llguanglisf.com` |
| `abappls-<edge>.llguanglisf.com` A/AAAA | **NXDOMAIN（Status=3）** |
| `<rand>.footcampbins.com`（SNI）A | `<AWS-apne1-IP>`（AWS ap-northeast-1） |
| `<AWS-apne1-IP>:14301/14330/14360/14374` TCP | **全部 ConnectionRefused** |

读法：

1. **节点域名在公共 DNS 里解析不到** —— 这正是 7.3.1 新增 `doh` 身份 + `dns.apexBootstrapClient` 的原因：
   客户端通过自己的 DoH 引导拿真实地址，第三方直接抄 `server` 字段会 NXDOMAIN。
2. SNI 域名解析到的 `<AWS-apne1-IP>` 不是 anytls 的监听面（端口全拒），说明它只是 TLS 前置/诱饵，
   真实落点仍要靠引导层。
3. 因此：**「订阅能拿到」与「节点能拨通」是两件事**。本轮验证的是前者（且已 100% 成立）；
   后者需要在客户端自身的引导链路里完成，或等拿到 7.3.1 的 OpenWrt 包用其 `RouterConfig` 反推引导参数。

#### 8.4.1 私有 DoH 的入口：找到了，但打不通

翻订阅的 `dns` 段能直接看到引导入口 —— 它在 **`proxy-server-nameserver`** 里，每次下载都会换一张新令牌：

```yaml
dns:
  proxy-server-nameserver:
    - "https://fbcg02.web.ak005.com/api-v2/<per-fetch-token>"
```

也就是说：**节点域名的解析不靠公共 DoH，而是靠这张按账号/按订阅签发的私有 DoH URL**。
这与 Go 内核里的 `dns.apexBootstrapClient` + `doh` 身份（`purpose=doh` 那张证书）正好对上。

本沙箱的实测（两次订阅、两个令牌、5 种证书 × 3 种路径 × GET/POST）：

| 尝试 | 结果 |
|---|---|
| `GET /api-v2/<tok>?name=<node>&type=A`（doh / sub / api / 无证书） | 一次 404 伪装页；多次 TCP 超时 |
| `POST /api-v2/<tok>` + `application/dns-message`（wireformat） | 同上 |
| `GET /api-v2/<tok>/dns-query` | 同上 |
| `fbcg02.web.ak005.com` 解析 | `103.239.185.80`，443 连接超时 |

结论：**入口已定位、协议形态已确认（DoH JSON + wireformat 双支持），但该主机在本网络不可达**，
且令牌与订阅强绑定（每次 download 轮换）。这条要在客户端进程内（同一 TLS 会话）或可达网络里才能打通；
不适合写进自动服务，只能作为"已知入口"记录。

## 9. 验证链深度补测（Aotopsy 反汇编 + 真实信封证伪）

> 本节回答一个问题：`docs/04` 里"签名与校验块已被还原"的说法，**有没有被端到端验证过**。

### 9.1 反汇编：7.3.1 确实在验签，也确实在跑 AES-GCM

用 `aotopsy signal` 对 Android `libapp.so`（Dart 3.12.2 / arm64）做全量反汇编（39,215 函数，
BLR 注释率 97.4%），`BoardDecryptHelper.open_260ce8` 的调用链如下（`call_edges.jsonl` 可复核）：

```
sub_1d038                      长度区间检查（0x69 ≤ len ≤ 0x1000000+0x69）
BoardDecryptHelper.isEnvelope  魔数/版本
ByteData.getUint32 ×2          aesKeyID / signKeyID（BE，逐字节读出后比较）
base64Decode ×2                两把 32B 键（反汇编里 CMP #0x40 是 Smi 长度检查）
sublist(0, len-64)             待验签消息体
Utf8Encoder("apex-sub-sign-" + "v2" + "\0")   前缀在运行时拼接
_GrowableList.addAll           msg = prefix ‖ body[0:len-64]
SimplePublicKey → Signature → DartEd25519.verify
sublist(25,…) / sublist(13,25) ct / nonce
new Mac → SecretBox(ct, nonce, mac) → DartAesGcm.decrypt
```

**结论一：`docs/04 §4.8`「它不是 GCM，只借用了计数器流」这条要改。**
GCM 的数据加密就是 `inc32(J0)=nonce‖0x00000002`，与 CTR 同一条流——"CTR 能解"与"它是 GCM"并不矛盾；
客户端调的确实是 `DartAesGcm.decrypt(SecretBox(ct, nonce, mac))`。

**结论二：`isEnvelope` 的长度边界（0x69 / 0x1000000+0x69）与文档完全一致**，这条文档是对的。

### 9.2 真实信封上的证伪（35,173 B，aesID=1 signID=1）

| 检验 | 组数 | 结果 |
|---|---|---|
| CTR 解密 `nonce‖2` | 1 | ✅ 35,068 B，YAML 合法，官方 `ApexCore -t` 通过 |
| Ed25519：`k2` + `"apex-sub-sign-v2"‖body[:-64]` | 1 | ❌ |

| 16 B vs md5/sha1/sha256/blake2b/HMAC/CMAC（明文与密文） | 14 | ❌ 全不等 |
| GHASH 实现校准（NIST SP800-38D 向量） | 1 | ✅ 实现无误 |

### 9.3 三种可能，需要运行时才能定论

1. 服务端用**另一把签名私钥**（内置 `k2` 只是默认值，实际密钥随 profile/配置下发）；
2. 尾部两段**不参与判定**（`verify` 失败被吞、`mac` 由本地重算而非取自信封）；
3. 信封布局与文档差 16 B（`ct` 实际取到 `len-64`），导致切片假设全偏。

无论哪种，**"用 k1 解密"这条生产路径不受影响**（官方内核已验证），
受影响的是"签名/校验块已被还原"这一表述的强度——已在本节降级为"代码路径存在、参数待定"。
