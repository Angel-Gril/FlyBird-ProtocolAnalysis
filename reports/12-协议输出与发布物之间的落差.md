# 12 · 协议输出与发布物之间的落差（与服务仓库的分界）

> 本文回答一个反复被问到的问题：**协议已经还原完了，为什么客户端还是连不上？**
> 结论：协议层到"解出 74 个节点"为止是完整的；从"节点"到"用户能打开网页"之间还有一段**发布层**，
> 它属于另一个仓库（服务实现），但它踩的坑源于协议本身的一个设计事实。
>
> 本文只记录**协议事实与验证方法**；服务仓库的部署、模板、缓存实现不在本仓库范围内。

---

## 12.1 两份仓库的分工

| 仓库 | 位置 | 负责 |
|---|---|---|
| **本仓库**（协议） | 上游 | 登录、凭据、APXS 信封、远程配置、签名/tag 校验、节点结构 |
| 服务仓库（实现） | 下游 | 把协议输出转成用户可用的订阅：分流模板、多格式导出、缓存、刷新、分发 |

协议仓库的边界是"**字节 → 数据结构**"；服务仓库的边界是"**数据结构 → 可用的网络配置**"。

---

## 12.2 协议层的既有事实（本仓库已闭环）

| 环节 | 状态 |
|---|---|
| 登录 / access-token / 下载 | ✅ |
| APXS v2 布局、GCM tag、Ed25519 签名 | ✅ 逐字节验通（`src/apxs_verify.py`） |
| `apex-config-v1` 解码与验签 | ✅ |
| 节点结构（类型、端口、SNI、密码） | ✅ |

到这一步，"解开订阅"这件事**没有未解项**。

---

## 12.3 关键设计事实：**入口地址不在信封里**

APXS 解码得到的节点形如：

```yaml
server: axbtapp-<rand>.llguanglisf.com   # 主机名，不含 A/AAAA 字面量
port: 14301
sni: <rand>.footcampbins.com
ip-version: ipv6-prefer                  # 只是拨号偏好，不携带地址
```

解析这个主机名需要：

1. 订阅 `dns.proxy-server-nameserver` 指向的 DoH 端点；
2. `purpose=doh` 的客户端证书（mTLS 身份）；
3. 官方内核里的私有重定向实现（`apexDohTLS` / `createClient.apexDohRedirect`）。

**这三样都是官方客户端专有的。** 换句话说：

> 协议**不承诺**"拿到订阅即可直连"。入口发现被显式划给了客户端。

这不是缺陷，是设计；但它决定了任何第三方消费者都必须自己补上"域名 → 可用地址"这一步。

---

## 12.4 由此产生的四类落差（发布层必须处理）

| # | 落差 | 表现 | 处理原则 |
|---|---|---|---|
| 1 | **地址不在信封内** | 第三方客户端 `dns resolve failed: couldn't find ip` | 发布前解析出地址并写入配置 |
| 2 | **客户端内核不同** | Mihomo 认 `hosts`；sing-box 无此表 | 按内核出两份产物，不要依赖客户端"转换" |
| 3 | **地址可用性因网络而异** | 同一 IP：境外可达、国内超时；或相反 | 逐 IP 探活，**标注验证视角**，不能拿服务端结论当判决 |
| 4 | **上游解析通道会抖** | 私有 DoH 间歇性黑洞（SYN 无响应） | 解析失败不得阻断发布；允许公共解析 + 探活兜底，并保留 last-known-good |

> 这四条都不是协议错误，但**只靠读协议永远发现不了**，必须做真实转发验证才会暴露。

---

## 12.5 验证纪律（本仓库建议的判据）

一次"能用"必须依次通过四关，任何一关不能替代下一关：

```
① 配置可加载   mihomo -t / sing-box check          ← 语法与引用完整性
② 域名可解析   A/AAAA 有答案，且不是 fake-ip/私网
③ 地址可连接   TCP 到节点端口（不是 443）
④ 真实转发     HTTP 200 + 期望出口地区              ← 唯一有判决力的一关
```

附加两条：

- **标注视角**：每个地址的可用性都带"(地址, 地址族, 验证来源, 时间)"；服务端在海外、没有 IPv6 时，它"验证不了 IPv6"不等于"IPv6 不可用"。
- **客户端回执优先**：只有用户网络里的真实请求成功，才能把该地址升为默认；其余保持候选。

---

## 12.6 本仓库收录什么、不收录什么

| 收录 | 不收录 |
|---|---|
| 协议格式、常量、校验算法 | 服务端部署、systemd、nginx |
| "入口地址不在信封内"这类设计事实 | 缓存实现、门禁代码、调度策略 |
| 四关验证判据与视角纪律 | 具体客户端（FlClash/Hiddify）的配置差异清单 |
| 失败模式归类（DNS / 地址 / 内核 / 转发） | 某一轮故障的逐条排查记录（放服务仓库的 reports） |

---

## 12.7 一句话结论

**协议回答"数据是什么"，发布层回答"用户连哪台机器"。** 本仓库已经把前者做完并验证；
后者反复出问题，是因为它要替官方客户端完成"入口发现"这件协议故意不做的事——
而这件事**没有一次性的答案**，只能靠"按 IP 探活 + 按视角记录 + 客户端回执"持续维护。
