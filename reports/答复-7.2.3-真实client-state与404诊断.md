# 答复：为什么 bundle 解出的是 `api.example.com`，以及如何拿到真实 client-state

> 对应分支：`feat/flybird-client-state-v723`（801bbd5 / becd20d）
> 结论先行：**磁盘/DPAPI bundle 路线在 7.2.3 上不可能拿到真实域名**——远程配置从不落盘。
> 真实域名已由运行态内存取证取回（两次复现），可直接作为 fixture 完成离线验收。

---

## 1. 根因：三层叠加，缺一不可

### 1.1 `api.example.com` 不在客户端任何产物里（全库 0 命中）

检索范围：`installed/data/app.so`、`apk/lib/arm64-v8a/libapp.so`、`installed/Apex.exe`、
`%APPDATA%\com.fbapp.clients.apex\**`、APK 解包目录。

| 字符串 | 命中 |
|---|---|
| `api.example.com` | **0** |
| `your-oss.example.com` | 1（仅 `assets/flutter_assets/assets/config/config.yaml` 模板） |
| `fbaxapi.*` / `fbaxsub.*` | 二进制 0，**仅在运行态内存中出现** |

=> 你 bundle 里的 `api.example.com` 是**工具侧默认值/模板回填**，不是客户端真实状态。
（客户端自带的模板原文是 `https://your-oss.example.com/config.json`，连 `api.example.com` 这个形状都没有。）

### 1.2 远程配置只在内存，不落盘（已做对照实验）

| 实验 | 结果 |
|---|---|
| 正常启动 20s → 全量转储（503 MB） | Dart 堆中找到 `apex-config-v1` 明文，含真实域名 |
| **清空 AppData + 防火墙阻断出站** → 启动 20s → 转储（218 MB） | `fbaxapi`/`fbaxsub`/`apex-config-v1` 明文 **0 命中**（只剩常量池里的键名） |
| 落盘文件 | `flutter_secure_storage.dat` 仅 **278 B**（DPAPI 包，存 profile 密钥，不含配置）；`shared_preferences.json` 无任何域名（两次运行仅差 `update_check_auto_last_at`） |

=> 配置是「拉取→解析成 Map→只活在内存」。**任何离线 bundle 导出都不可能带出真实域名**，
除非导出的是进程内存。

### 1.3 于是「占位域名 + DNS 不存在」不是服务问题，是采集源问题

## 2. 真实 client-state（本 build 实测，可直接用作 fixture）

文件：`reports/client-state-7.2.3.json`（format `apex-client-state/v1`，`source: runtime-memory`，`live_verified: false`）

```json
{
  "panel_type": "xboard",
  "enable_api_path_mapping": true,
  "api_domains": ["https://fbaxapi.web.ak005.com", "https://fbaxapi.apiv2.a047.com"],
  "subscribe_domains": ["https://fbaxsub.web.ak005.com", "https://fbaxsub.apiv2.a047.com"],
  "path_map": { "...32 条...": "" },
  "features": { "...": "" },
  "contact": { "website": "https://web01.fbbapp.cc", "...": "" }
}
```

关键三条（与你的实现对齐）：

```
登录        POST {api_domains[0]}/v2/auth/token
凭据        GET  {api_domains[0]}/v2/feed/access-token   (Bearer <token|auth_data>)
下载        GET  {subscribe_domains[0]}/v2/feed/download?access_key=<key>
```

- API 与订阅是**两组独立域名**（你的判断正确）；
- 顺序即故障转移顺序（web.ak005.com → apiv2.a047.com）；
- `access_key` 才是可长期复用的凭据，`xboard_token` 只是短期登录态（你的判断正确）。

## 3. 可达性诊断：404 ≠ DNS 不存在

四个域名全部 **CNAME 到同一台边缘 `<edge-ip>`**：

```
fbaxapi.apiv2.a047.com → axapi-cn.apiv2.a047.com → <edge-ip>
fbaxapi.web.ak005.com  → axapi-cn.web.ak005.com  → <edge-ip>
fbaxsub.*              → 同上（订阅与 API 同边缘）
```

实测（2026-10-25）：

| 探测 | 结果 | 含义 |
|---|---|---|
| DNS | 正常解析（CNAME→A） | **域名存在**，不是 NXDOMAIN |
| TLS 握手 | 成功（证书可协商） | 边缘存活 |
| `Host:` 改成不存在的名字 | **421 Misdirected Request** | 边缘按 Host 路由，**vhost 配置存在** |
| `GET /`、`/v2/*`、`/api/v1/*` | 一律 **404 nginx/1.30.6** | 源站没有对应路由 |
| 加内嵌 mTLS 客户端证书（api/subscription） | 仍 404 | 不是 mTLS 门禁 |
| 加全套 `X-Client-*` 指纹头 | 仍 404 | 不是风控头门禁 |

结论：**边缘在、vhost 在、后端路由不在**。要么 v2 网关已迁移到新域名/新前缀，要么当前 IP 段被下发 404（地区/风控策略）。
所以你现在的失败点应记作「origin/route 404」，而不是「DNS 不存在」——这两者对验收结论的影响不同。

## 4. 如何拿到"当前"远程配置（可复现）

**重要事实**：本环境里客户端**确实成功拉到了**配置（两次：503 MB / 499 MB 转储都含真实域名），
而我们用 curl/requests 对同样的镜像 URL 一律 404 —— 说明差异在客户端 TLS 栈/边缘策略，不在 URL。

### 4.1 推荐：内存取证（已在 Windows 上复现两次）

```powershell
# 1) 全新状态（删/改名 %APPDATA%\com.fbapp.clients.apex）后启动客户端，等 15~25s
# 2) 管理员转储
rundll32 C:\Windows\System32\comsvcs.dll, MiniDump <PID> apex.dmp full
# 3) 回收
python poc\scrape_runtime.py apex.dmp --out recovered
```

注意：转储时客户端必须**已经成功拉过一次**；断网时内存里就是空的（已实验证）。

### 4.2 Android 侧抓包（可拿到密文，进而拿到 XOR_KEY）

`AndroidManifest` 的 `network_security_config` 只信 system CA，`assets/cer/` 为空（无 pinning 数据）：
把 mitmproxy CA 装进 `/system/etc/security/cacerts`（root/模拟器）即可解出
`fb_apex.json` 的请求 URL 与响应体。

### 4.3 拿到一次密文后：永久离线解密

`poc/recover_xor_key.py`（自测通过，支持三种层序）：

```
A) wire = base64( XOR( envelope, K ) )
B) wire = XOR( base64( envelope ), K )
C) wire = XOR( envelope, K )
```

```powershell
python poc\recover_xor_key.py --cipher raw_fb_apex.bin --payload recovered\apex_config_*.json --out xor_key.bin
```

有了 K，以后任何一次 `fb_apex.json` 都能离线解——不再依赖客户端在线。
（本轮没拿到密文：两次转储里响应体已被 GC，只剩解析后的 Map。）

## 5. 对分支/推送的建议

1. **不要把占位域名写进测试期望值**，也不要用它做"部署成功"判据。
2. 把 `reports/client-state-7.2.3.json` 收进 `tests/fixtures/`，字段：
   `source=runtime-memory`、`live_verified=false`、`captured_at`、`build.version=7.2.3+1792857411`。
   验收口径写成：**解析/解密/路径改写 100% 通过；在线拉取标记 pending（附 404 证据）**。
3. 增加 `--state-fixture` 与 `--require-live` 两个开关：fixture 模式可完全离线跑；`--require-live` 在
   拿到可达域名后再开，避免把"占位域名可用"写死。
4. 在线验收再开一档：拿到一次可达响应后，用 §4.3 的 key 固化，之后 CI 用「录制响应 + key」回归，
   不需要每次打真网。
