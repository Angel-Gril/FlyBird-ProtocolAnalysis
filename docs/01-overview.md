# 01 · 研究目标与方法论

## 1.1 背景

目标客户端（下称 "FB 客户端"）是一款多平台的代理服务前端。它从服务端拉取订阅，
订阅内容是加密的 **APXS v2** 信封，解密后才是标准的 Clash/mihomo YAML。
客户端不提供任何导出功能，官方文档明确写着：

> 账号密码、登录 Token 和节点只在内存中使用，不写入 UCI、浏览器存储或 config.yaml。

这意味着：**"不落盘"是它对订阅明文唯一的保护**。

## 1.2 研究问题

| # | 问题 | 为何重要 |
|---|---|---|
| Q1 | 订阅交付链路的完整形态是什么？ | 决定能否脱离 GUI |
| Q2 | APXS 的加密算法与密钥从哪来？ | 决定能否本地解密 |
| Q3 | 客户端的"内存only"控制是否有效？ | CWE-602 评估 |
| Q4 | 是否存在不依赖客户端二进制的实现路径？ | 可移植性/可维护性 |

## 1.3 方法论

采用四阶段递进：

```
阶段一  黑盒测绘
        ├─ 域名与端点枚举（证书透明度日志、DNS、SNI 抓包）
        ├─ UA / Header / 证书矩阵（差分响应）
        └─ 建立"什么条件下返回真实数据"的最小条件集

阶段二  静态逆向
        ├─ Windows: Inno Setup 解包 → PE 分析
        ├─ Android: Flutter AOT → Blutter 反编译 Dart
        ├─ Linux: GTK 客户端 → 符号/字符串
        └─ OpenWrt: Go 二进制 → pclntab 符号恢复

阶段三  动态取证
        ├─ 进程内存扫描（Windows/Linux）
        ├─ TLS 终止观察代理（记录真实请求序列）
        ├─ netns 隔离运行（避免污染宿主网络）
        └─ gdb 断点（抓函数入参与返回值）

阶段四  协议复现
        ├─ 用恢复出的算法本地解密
        ├─ 与官方输出逐字节比对
        └─ 服务化（systemd + 定时刷新 + 原子发布）
```

## 1.4 关键判据

研究中坚持三条判据，避免"看起来像"的结论：

1. **可复现**：任何结论必须能用仓库内代码重现；
2. **逐字节可比对**：解密结果必须与官方客户端输出完全一致（不是"能解析"就算对）；
3. **失败也是结论**：7 万种密钥组合失败、4000 万内存窗口 0 命中，这些否证同样记录在案。

## 1.5 结论摘要

- 订阅交付链路的真实条件集是 `客户端证书(purpose 匹配) + 特定 UA + 裸 JWT`，三者缺一即 404；
- APXS 使用 **AES-256-CTR**，密钥为客户端内置常量，与账号无关；
- "不落盘"控制有效范围仅限于**磁盘取证**，对**同机 root 进程内存读取**无效；
- 存在不依赖任何客户端二进制的纯协议实现，单次 8 秒。
