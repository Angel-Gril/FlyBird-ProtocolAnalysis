# 07 · 安全评估与加固建议（CWE-602）

> 本文从**防守方**视角评估这套设计：哪些控制有效、哪些形同虚设、该怎么改。

---

## 7.1 威胁模型

| 攻击者能力 | 是否能拿到订阅明文 |
|---|---|
| 能读磁盘（备份、取证镜像） | ❌ 拿不到（客户端不落盘）✅ 该控制有效 |
| 能抓包（同网段） | ❌ 拿不到（TLS + mTLS + pinning）✅ 有效 |
| 能读客户端安装目录 | ✅ 拿到证书（可直接复用）⚠️ 中等 |
| 能在同机以 root 运行进程 | ✅ **完全拿到**（读进程内存）❌ 无效 |
| 能改客户端二进制 | ✅ 拿到（打补丁导出）❌ 无效 |

**结论**：这套控制只防"离线取证"，不防"同机运行时"。

## 7.2 各道防线的实际效果

| # | 控制 | 设计意图 | 实测效果 |
|---|---|---|---|
| 1 | TLS + 证书 pinning | 防中间人 | **有效**（自签 CA 被拒） |
| 2 | mTLS 双向证书 | 防未授权客户端 | **弱**（证书在客户端目录，可复制） |
| 3 | UA 门禁 | 防脚本 | **无效**（公开字符串，一行 header 即可） |
| 4 | 404 伪装 | 隐藏接口 | **弱**（差分测试即可还原条件集） |
| 5 | 订阅加密（APXS） | 防抓包重放 | **无效**（密钥在客户端内） |
| 6 | Ed25519 签名 | 防篡改 | **有效**（改一个字节就验签失败） |
| 7 | 明文不落盘 | 防磁盘取证 | **有效**（但内存可读） |
| 8 | swap 检查 / tmpfs 强制 | 防内存落盘 | **有效**（但阻止不了直接读内存） |
| 9 | 控制口脱敏（`state` 只返回白名单 DTO） | 防导出 | **有效**（API 层面拿不到节点） |

关键洞察：**第 9 条做得好，但第 7 条是唯一真正的防线，而它防不住 root。**

## 7.3 核心问题：密钥在客户端

APXS 的 AES 密钥是**硬编码常量**，所有用户共享。这意味着：

- 任何人逆向一次，就能解密**所有**用户的订阅；
- 密钥轮换需要全量客户端升级；
- 加密实际只提供"防抓包"，不提供"防逆向"。

**这是 CWE-602 的典型形态**：把机密性依赖放在不可信端。

## 7.4 加固建议（按性价比排序）

### P0 · 把"订阅明文"变成"服务端决策"

最彻底的做法：客户端不再持有完整节点凭据。

```
现状：  服务端 --(完整 YAML)--> 客户端 --(内核)--> 流量
建议：  服务端 --(短期票据)--> 客户端 --(每连接向服务端要凭据)--> 内核
```

或者干脆做成**服务端转发**（客户端只是一个本地 SOCKS，不认识节点）。

### P1 · 每设备独立密钥 + 服务端解密

- APXS 改为**按设备密钥**加密（客户端生成密钥对，公钥注册到服务端）；
- 吊销单设备即可，不用全量升级；
- 成本：多一次密钥协商。

### P2 · 内存最小化与即时擦除

```go
// 现状：整份 YAML 长时间驻留
cfg, _ := OpenAPXS(body, ident)
applyConfig(cfg)

// 建议：解析后立即擦除原始缓冲
defer func() {
    for i := range body { body[i] = 0 }
    runtime.KeepAlive(body)
}()
```

并避免 `string` 化（Go 的 string 不可变，会长期驻留，应用 `[]byte` + 手动清零）。

### P3 · 反调试 / 反 dump（提高门槛，不解决问题）

```go
// TracerPid 检查
// ptrace(PTRACE_TRACEME) 占位
// 关键函数用 //go:noinline 并校验调用栈
```

对专业逆向者无效，但能挡住大部分脚本化尝试。

### P4 · 只下发"渲染结果"

如果产品允许，把规则/分组/策略放在服务端，客户端只拿"最终可用的节点列表"，
并且**节点凭据按连接短期签发**（类似短期 token）。
这样即使客户端被完全逆向，泄露面也只有"当前会话"。

### P5 · 密钥不要硬编码

如果必须用对称加密，至少让密钥**按账号派生**：

```
key = HKDF(server_secret, account_id || device_id)
```

这样逆向一个客户端拿不到全局密钥。

## 7.5 我们验证过的"无效加固"

以下措施在实测中被证明没有实际防护价值（不建议投入）：

| 措施 | 为何无效 |
|---|---|
| UA 门禁 | 公开字符串，抓一次包就有 |
| 404 伪装 | 差分测试可还原条件集 |
| 证书 purpose 绑定 | 证书都在客户端目录，可复制 |
| 不落盘 | root 可读内存 |
| 控制口脱敏 | 只防 API 层导出，不防内存 |

## 7.6 对研究者的建议

1. **优先做"能不能拿到"的判定，而不是"怎么绕"**；
2. 每一步都保留原始证据（抓包、dump、反编译输出），便于复核；
3. 结论要能被否证——我们推翻过自己两次（"密钥由服务端下发"、"GCM AEAD"）；
4. 测试环境隔离（netns / 虚拟机），避免影响生产；
5. 结束后清理：还原 hosts、CA、防火墙、swap，删除测试文件。
